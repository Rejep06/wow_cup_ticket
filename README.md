# WOW CUP — мониторинг билетов с автообновлением ссылки

Мониторит билеты на **WOW CUP: Медведев vs Рублёв**, 5 декабря 2026 г., Москва. В переданном примере актуальная запись — **17:30 МСК** (`session.id=143823287`), доступных билетов **0** на момент этого ответа API. Бот не делает вывод о текущем наличии по старому снимку: при работе он запрашивает данные снова.

Бот отправляет Telegram-уведомления нескольким получателям, если в *конкретном сеансе* `result.session.availableSeatCount > 0`. Никакого автоматического бронирования, платежей или обхода SmartCaptcha здесь нет.

## Что изменилось по сравнению с предыдущей версией

1. Сам получает ссылку продажи с `https://wowcup.tennis/`. В HTML ищет `ticketUrl` из `window.__NUXT__.config.public` (дополнительно понимает JSON-подобную запись, HTML-ссылки и Nuxt-скрипты с того же сайта).
2. Составляет URL GET API по ссылке на виджет, например:
   - widget: `https://widget.afisha.yandex.ru/w/sessions/ticketsteam-8261@77813737?clientKey=...&regionId=213`
   - read API: `https://widget.afisha.yandex.ru/api/tickets/v1/sessions/ticketsteam-8261@77813737?clientKey=...&req_number=0`
3. Раз в **10 минут** перечитывает официальный сайт, даже если API работает. На HTTP **404** или другом сбое API дополнительно перечитывает сайт сразу. Если ссылка изменилась, автоматически повторяет проверку **по новому API URL**.
4. Если сайт недоступен, использует последнюю корректную ссылку из `data/state.json` или резервную `TICKET_URL` из `.env`.
5. Если ссылка осталась прежней, но API всё ещё ошибается, увеличивает интервалы: **2, 4, 8, 16, 32, 60, 60... минут**. После успешного API-ответа возвращается к **60 секундам**. Для HTTP 429 соблюдает заголовок `Retry-After` (он может запросить паузу больше часа).
6. Отдельно уведомляет об изменении ссылки, **не утверждая**, что билеты появились. Изменение URL само по себе — не наличие.
7. Устраняет проблему несовпадающих идентификаторов: `ticketsteam-8261@77813737` в URL не равен `session.key` в API, и это нормально. Вместо ошибочного сравнения бот проверяет `event.id`, дату, `session.id` и данные о доступных местах.
8. Если JSON стал непонятным, пришёл HTML, капча или отказ сервера, **не пишет «билетов нет»**: считает проверку неуспешной и оповещает после нескольких ошибок.

**Ограничение:** если Яндекс полностью поменяет внутренний API, но *адрес виджета останется тем же*, бот не может самостоятельно узнать произвольный новый внутренний протокол. Он предупредит об ошибках и сохранит последнюю ссылку. Тогда потребуется изучить запросы новой версии виджета в DevTools. Доступ к антибот-защите, очереди и CAPTCHA бот не обходит.

## Обновление старого бота

1. Сохраните старый `.env` (Telegram токен и chat IDs). Из нового архива замените `watcher.py` и при желании `README.md`/`test_watcher.py`.
2. Добавьте в **существующий** `.env` эти строки, подставив полную ссылку (пример ниже уже подходит для указанного сеанса):

```env
LANDING_URL=https://wowcup.tennis/
TICKET_URL=https://widget.afisha.yandex.ru/w/sessions/ticketsteam-8261@77813737?clientKey=5a2f3e1d-f923-4b55-8a34-636ba6dfe922&regionId=213
EXPECTED_EVENT_ID=908192
EXPECTED_DATE=2026-12-05
DISCOVERY_INTERVAL_SECONDS=600
CHECK_INTERVAL_SECONDS=60
MAX_ERROR_INTERVAL_SECONDS=3600
NOTIFY_URL_CHANGES=true
```

3. Удалите из `.env` **устаревшие** `SESSION_KEY` и `CLIENT_KEY`. Они сохранены лишь для совместимости; если указана `TICKET_URL`, она имеет приоритет как резервная ссылка. Ссылка с официального сайта имеет наивысший приоритет в любом случае.
4. Сохраните папку `data/`, чтобы не потерять счётчик ошибок и состояние уведомлений. При обнаружении нового сеанса счётчик прошлых доступных билетов сбросится корректно.
5. Перезапустите процесс или Docker:

```bash
docker compose up -d --build --force-recreate
docker compose logs -f watcher
```

**Важно:** старый `.env` не нужно заменять целиком — иначе потеряете токен и chat IDs.

## Первая установка

Python 3.10+.

```bash
python -m venv .venv
# Linux/macOS
source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env
```

Вставьте токен от [@BotFather](https://t.me/BotFather) и всех получателей через запятую:

```env
TELEGRAM_BOT_TOKEN=123456789:YOUR_TELEGRAM_BOT_SECRET
TELEGRAM_CHAT_IDS=123456789,987654321,-1001234567890
```

Каждый пользователь предварительно отправляет боту `/start`. ID можно получить командой `python watcher.py --chat-id`.

Диагностика:

```bash
python watcher.py --discover   # URL из wowcup.tennis + адрес API
python watcher.py --once       # одно чтение API; Telegram не требуется
python watcher.py --test       # проверка рассылки всем chat IDs
python -m unittest -v         # 26 локальных тестов; без сети
python watcher.py             # непрерывный мониторинг
```

Для VPS / Docker:

```bash
docker compose up -d --build
docker compose logs -f watcher
```

Остановка: `Ctrl+C` или `docker compose down`.

## Настройки

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `LANDING_URL` | `https://wowcup.tennis/` | Официальная страница, источник `ticketUrl` |
| `TICKET_URL` | Указанный новый виджет | Резервная ссылка, когда сайт недоступен; автоматически обновляется из HTML |
| `TELEGRAM_BOT_TOKEN` | — | Токен Telegram (секрет) |
| `TELEGRAM_CHAT_IDS` | — | Несколько ID через запятую |
| `CHECK_INTERVAL_SECONDS` | `60` | Пауза между успешными проверками (не меньше 30) |
| `DISCOVERY_INTERVAL_SECONDS` | `600` | Как часто обновлять URL с сайта (не меньше 60) |
| `MAX_ERROR_INTERVAL_SECONDS` | `3600` | Максимум backoff в секундах, если сервер не предписал более длинную паузу |
| `ERROR_ALERT_THRESHOLD` | `3` | Через сколько неудачных проверок предупредить |
| `ALERT_COOLDOWN_SECONDS` | `900` | Ограничение частоты сообщений об увеличении количества билетов |
| `EXPECTED_EVENT_ID` | `908192` | Защита от переключения на другое событие |
| `EXPECTED_DATE` | `2026-12-05` | Защита от переключения на другую дату |
| `NOTIFY_URL_CHANGES` | `true` | Отдельное информирование об изменении ссылки |
| `STATE_FILE` | `data/state.json` | Состояние, кэш ссылки, интервалы, доставка |

## Когда бот отправляет уведомления

- При старте — тестовое сообщение о начале мониторинга.
- Когда `session.availableSeatCount` изменился с `0` на положительное число, либо билеты найдены при первом запуске.
- При увеличении числа мест — с ограничением по cooldown.
- При смене официальной ссылки — **информация**, не ложный сигнал наличия.
- После трёх неудач API подряд — предупреждение; после успешного восстановления — сообщение о восстановлении.
- Если сообщение не дошло до части получателей, бот пробует повторить **только неудавшимся**.

Не ориентируйтесь на `event.saleStatus = "available"` или `sessionServices[].saleStatus = "available"`. Эти поля могут показывать `available`, когда в конкретном сеансе `availableSeatCount=0`.

## Безопасность и ограничения

- Запросы делаются лишь к официальному HTTPS-домену виджета, указанному на сайте турнира. Не загружайте произвольные ссылки из неофициальных источников.
- Бот выполняет только публичные GET-запросы, без платёжных действий, очередей и CAPTCHA.
- Уважайте ограничения сервиса, не ставьте слишком маленькие интервалы и не запускайте несколько одинаковых процессов с одним аккаунтом.
- Это не документированный публичный API; формат и правила могут поменяться. Локальные тесты не подтверждают доступность сайта и API в данный момент.
- Не выкладывайте `.env`, логи с конфиденциальными данными или токен Telegram.
