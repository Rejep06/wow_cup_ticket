# WOW CUP Checkout Assistant v6 — экспериментальная версия

**Это отдельный прототип браузерного оформления, а не доказанно работающий клиент бронирования Яндекса.** Он создан по предоставленным ответам виджета и исходному `tickets_finder`. Архивы v4/v5 в текущем окружении недоступны; бинарная совместимость и миграция их состояния не заявляются.

Здесь есть исполняемый мониторинг, поддержка v4 hallplan → CDN, браузерный адаптер, наблюдение за созданием/резервированием заказа, бюджетные ограничения и локальные тесты. **Успешная живая бронь/переход к QR-коду WOW CUP не проверены.** Разметка корзины и полная схема Request Payload не предоставлены: стандартные CSS-селекторы в `ui.json` — кандидаты. При несовпадении скрипт передаёт управление человеку, а не нажимает случайную кнопку.

## Что показал предоставленный лог

Фактическая последовательность: preview `PROCESSING` → `orders/create` с ID и `booked:false`, `approved:false` → `operation/reserve` несколько раз `running` → `failed`, `statusCode: order-validation-failed` → `cancel` с `status:success`.

Это **не успешное резервирование**. Наличие ID, HTTP 200, внешнего `status:success`, положительного таймера или `recreateOrderEnabled:true` не доказывает бронь. Точная причина `order-validation-failed` из этих ответов не определяется. Не следует автоматически приписывать её CAPTCHA, неправильным контактам или чужой покупке.

В логе одновременно менялись числовой session.id и extSessionId. Программа не закрепляет их навсегда: для схемы берётся текущий session.key, а места проверяются по текущим идентификаторам поставщика. Статическая схема `storage.mds...` содержит геометрию, а не список свободных мест.

## Реализованная цепочка

1. Публичный сеанс читается с проверкой event ID и даты.
2. При положительном сигнале сразу читается `/api/tickets/v4/sessions/{key}/hallplan`; при `completed` используется возвращённый свежий CDN URL. Старый CDN hash не опрашивается бесконечно. При `running` допускаются максимум три чтения этой операции с паузой 2 с.
3. Выбираются 1–2 места в бюджете, учитывается известная комиссия; по желанию — только соседние, без большого промежутка по координатам. Обязательные связанные комплекты и входные билеты без мест не поддержаны этим адаптером.
4. Уже открытый Chromium переходит по selectedSeats. Перед каждой автоматической кнопкой проверяются текст корзины, ряд/место, сектор и итоговая сумма. Неизвестная разметка останавливает автоматику.
5. Виджет сам создаёт запросы оформления с актуальной сессией. Python НЕ повторяет старые JWT и НЕ составляет выдуманный POST.
6. `orders/create` и `operation/reserve` наблюдаются отдельно. После неизвестного результата, неуспешного резерва, CAPTCHA или готовности оплаты новые заказы не создаются. CAPTCHA требует ручного решения; после него Enter в терминале может продолжить текущий сценарий без повторного создания заказа.
7. На этапе оплаты браузер передаётся владельцу. Программа не вводит карту, не работает с банковским приложением, не подтверждает платёж.

### Особый режим подготовки СБП

`AUTO_START_SBP=true` разрешает распознанную кнопку «Оплатить СБП» либо «Оплатить» после выбора radio с DOM value `new-sbp-token`. Корзина должна пройти проверки. На выходящий `orders/create` установлен дополнительный ограничитель: **только один POST**, `paymentWay: new-sbp-token` на верхнем уровне тела, без идентификатора сохранённого способа оплаты. Неизвестная схема → `CREATE_GUARD_STOP` и ручное управление.

Расположение `paymentWay` на верхнем уровне — **консервативное условие допуска, НЕ установленный контракт API**. Реальный Request Payload в переписке отсутствует. Если виджет отправляет другую структуру, этот прототип намеренно не продолжает автоматически. Не следует просто выключать ограничитель: нужен обезличенный образец реального запроса, чтобы изменить проверку осознанно.

Ни `orders/create`, ни `reserve`, ни `cancel` напрямую не вызываются Python-кодом. Проверка статуса текущего резерва остаётся за официальным виджетом. Банковский платёж подтверждает человек.

## Установка на Windows / PowerShell

Остановите старые экземпляры v3/v4/v5. Проверьте вручную, что у вас нет действующего заказа. Блокировка v6 не видит другой бот в другой папке.

```powershell
cd yandex_tickets_checkout_v6
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m playwright install chromium
Copy-Item .env.example .env
```

Заполните `.env`: Telegram-токен, список chat_id, chat_id владельца, ФИО/email/телефон и **оба лимита цены**. Не переносите `.env` и профиль в публичные репозитории. Контакты из переписки намеренно не включены в архив.

Проверка логики без сетевых запросов:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -v
```

По умолчанию 4 необязательных браузерных теста будут пропущены. Они требуют переменной `TEST_BROWSER_PATH` с путём к установленному Chromium. Остальные тесты — полностью локальные.

Подготовьте отдельный профиль браузера:

```powershell
.\.venv\Scripts\python.exe watcher.py --setup
```

Откроется виджет. Войдите в свой аккаунт, если это нужно, пройдите проверку, затем нажмите Enter в терминале. Сохранение профиля **не гарантирует**, что CAPTCHA не появится снова или токен останется действительным.

Однократное чтение без оформления:

```powershell
.\.venv\Scripts\python.exe watcher.py --check
.\.venv\Scripts\python.exe watcher.py --test
```

**Первый рекомендуемый проход — диагностика, не включённая вслепую автопокупка:**

```powershell
.\.venv\Scripts\python.exe watcher.py --capture
```

В этом режиме скрипт сам ничего не нажимает; пользователь проходит шаги вручную. После Enter сохраняются `data/diagnostics.jsonl` (обезличенная структура запросов/ответов) и `data/ui-structure.json` (структура элементов без значений полей). Проверьте оба файла перед передачей. Полный HAR и cookies не нужны.

После проверки селекторов/запроса можно включить:

```env
AUTO_BOOKING=true
AUTO_START_SBP=true
BOOKING_HEADLESS=false
BOOKING_SEATS=1
CHECK_INTERVAL_SECONDS=10
POLL_JITTER_FRACTION=0.10
```

Затем:

```powershell
.\.venv\Scripts\python.exe watcher.py
```

Для Linux команды аналогичны с `python3` и `.venv/bin/python`. Для ручной CAPTCHA и оплаты нужен доступный графический рабочий стол. Автоматическое оформление в headless-режиме намеренно запрещено. Docker-развёртывание для невидимого фонового оформления здесь не предлагается.

## Частота и задержки

Интервал основного мониторинга по умолчанию **10–11 секунд**, без параллельных циклов и догоняющих всплесков. Нижний программный порог — 10 секунд. Это инженерная настройка прототипа, **не опубликованный лимит Яндекса и не обещание отсутствия блокировки**. При необходимости установите 30–60 секунд или согласованный с сервисом интервал.

Одна проверка в секунду означала бы 86 400 циклов в сутки; одна в 10 секунд — до 8 640 до учёта jitter, ошибок и остановок. Цикл не равен одному HTTP-запросу: появляются чтения hallplan/CDN и собственные запросы браузерного виджета.

Ускорение после обнаружения места достигается без дополнительной нагрузки на постоянный опрос: браузер уже запущен; нет двойного GET-подтверждения и искусственной паузы 3 секунды; Telegram отправляется независимой очередью; логика детерминированная, без вызова ИИ. Проверки DOM каждые 0.2 секунды — локальные, НЕ сетевой опрос каждые 0.2 секунды. Реальное время оформления на сервере не измерено.

При обычных ошибках чтения: 2, 4, 8, 16, 32, 60 минут, затем по часу до успешного чтения. HTTP 429: минимум 5 минут и обязательный `Retry-After`, даже если он больше часа. HTTP 401/403 и явная CAPTCHA требуют ручного вмешательства; fallback по другим маршрутам, смена IP/аккаунта и обход защиты не выполняются. Дата следующей проверки сохраняется при перезапуске. Опрос сайта wowcup.tennis ограничен отдельно: не чаще 10 минут.

Управляемый код не меняет антибот-JWT, не решает CAPTCHA, не подставляет украденные cookies, не использует stealth/прокси-ротацию и не обходит очередь. Сайт может применить ограничения при любом выбранном интервале.

## Состояния

| Состояние | Значение |
|---|---|
| ORDER_CREATED | Есть ID созданного заказа, но нет подтверждения резерва |
| RESERVING | Операция reserve вернула running |
| RESERVE_FAILED | Внутри успешного HTTP/JSON-ответа операция завершилась failed |
| CANCELLED | Наблюдался успешный ответ отмены данного заказа |
| RESERVE_COMPLETED_REPORTED | Операция сообщила success/completed; сами эти успешные варианты не представлены в исходном логе |
| PAYMENT_UI_READY | Совпали проверенный заказ, сообщение о завершении reserve и распознанная платёжная форма |
| PAYMENT_UI_UNVERIFIED | Платёжная форма видна, но недостаточно подтверждающих данных о заказе |
| RESERVE_REPORTED_PAYMENT_UI_NOT_RECOGNIZED | Ответ резерва распознан, но платёжная разметка не подтверждена адаптером |
| CREATE_GUARD_STOP | Отправка не соответствует безопасному ограничителю или повторяется |
| NEEDS_UI_ADAPTER | Не распознаны корзина/кнопки; нужен реальный DOM/селекторы |
| ORDER_RESULT_UNKNOWN | Запрос мог уйти, результата нет; повторно создавать заказ опасно |

Для QR-кода СБП задаётся точный `payment_ready_selector` в `ui.json` **после осмотра реальной страницы**. Сейчас он пуст. Один лишь текст «Способ оплаты» не считается платёжной формой и не доказывает резервирование.

После любой попытки оформление передаётся человеку, мониторинг останавливается. Нельзя бесконечно повторять `order-validation-failed`, создавать новые заказы вместо проверки старого или удерживать места повторными резервами. После проверки/отмены/истечения заказа можно явно сбросить локальную остановку:

```powershell
.\.venv\Scripts\python.exe watcher.py --reset-attempt
```

Нужно ввести `ПРОВЕРЕНО`. Это **не отменяет серверный заказ**. Не удаляйте `data/state.json` автоматически. После успешной покупки не перезапускайте мониторинг для того же заказа.

## Конфиденциальность и уведомления

Общие сообщения идут в `TELEGRAM_CHAT_IDS`; сообщения о ходе/результате оформления — только в `BOOKING_OWNER_CHAT_ID`. Ссылка на приватный платёж и контакты не рассылаются нескольким людям. Оплачивать следует в том же окне Chromium: переносимость заказа по ссылке в другой браузер не подтверждена.

`data/browser-profile/` содержит данные авторизации, `state.json` может содержать ID заказа и наблюдённый URL. **Никому их не передавайте.** Держите весь `data/` приватным. Диагностика не сохраняет raw headers, cookies, полный JWT, тела ответов или значения полей. Очередь Telegram хранится отдельно, повторяет сообщения только недоставленным получателям и удаляет устаревшие уведомления. При сетевом таймауте возможен дубль уведомления; это не создаёт дубль заказа.

## Что необходимо для проверенного прямого API-клиента

Не нужны новые ответы Метрики, user-профиля или статической схемы. Нужны **Request Method, Content-Type, обезличенный Request Payload** у `session-order-preview/` и `tickets/v2/orders/create`; для первого reserve — Method и Payload, если он есть. Также нужны полный ответ preview и успешный переход reserve → страница/ответ оплаты. В доступных вложениях два упомянутых preview-ответа отсутствовали.

Удалите Authorization, Cookie, JWT, антибот/CSRF/платёжные токены, ФИО, email и телефон. Оставьте названия полей, структуру объектов, единицы стоимости и не секретные enum-значения вроде paymentWay. Не проводите платёж ради диагностики и не создавайте серию резервов на другие события.
